# Практическая работа № 2. Автоматизация тестирования REST API

Выбрал локальный API задач: так результат не зависит от доступности чужого
сервиса и его тестовых данных. Написал сценарии на pytest и добавил генерацию
запросов по OpenAPI через Schemathesis. Решение находится в ветке `lab2`.

## Запуск

Нужен Python 3.12 или 3.14. Команды для macOS/Linux:

```bash
python3 -m venv .venv
source .venv/bin/activate
python -m pip install -r requirements.txt
python -m pytest -v --cov=app --cov-report=term-missing
```

Сервер для тестов запускать не нужно: TestClient передаёт HTTP-запросы прямо
ASGI-приложению. Зависимости нужны при установке, сам прогон работает без сети.
В `requirements.txt` зафиксировал версии, в `requirements.in` оставил прямые зависимости.

Отдельные группы проверок:

```bash
python -m pytest -m api -v
python -m pytest -m contract -v
python -m ruff check .
python -m ruff format --check .
```

Для ручной проверки API:

```bash
python -m uvicorn app.main:app --reload
curl -i -X POST http://127.0.0.1:8000/tasks \
  -H 'Content-Type: application/json' \
  -d '{"title":"Сдать лабораторную","priority":2}'
```

Swagger UI доступен по адресу `http://127.0.0.1:8000/docs`.

## Что проверил

| Сценарий | Ожидаемый результат |
| --- | --- |
| Создание и чтение задачи | `201`, `Location`, затем `200` и те же поля |
| Создание только с названием | Приоритет `3`, признак выполнения `false` |
| Пустой список | `200` и `[]` |
| Пагинация и смещение за конец списка | Нужный срез; за концом — `[]` |
| Полная замена через PUT | `200`, прежний ID, новые значения сохраняются |
| Удаление и повторное обращение | `204` без тела, затем `404` |
| Несуществующая задача | GET, PUT и DELETE возвращают `404` |
| Границы названия и приоритета | Длины `1`/`100` и приоритеты `1`/`5` принимаются |
| Пустое, пробельное или длинное название | `422`, указано ошибочное поле |
| Пропущенное поле, `null`, неверный тип, лишнее поле | `422`, данные не меняются |
| Повреждённый JSON | `422`, новая задача не появляется |
| Неположительный или нечисловой ID | `422`, ошибка в параметре пути |
| Границы пагинации | `limit=1`/`100`, `offset=0` принимаются |
| Некорректная пагинация | `limit=0`/`101`, отрицательный offset и строки дают `422` |
| Генерация по OpenAPI | Проверка статусов, Content-Type, структуры ответа и обработки ошибок |

Проверяю не только статус: сравниваю тело ответа, заголовки и состояние после
изменяющих запросов. Обычные тесты получают новое приложение через fixture.
В генеративных тестах создаю приложение для каждого примера Hypothesis:
fixture уровня функции создавалась бы только один раз на всю серию примеров.

## API и контракт

| Метод | Путь | Успешный ответ |
| --- | --- | --- |
| POST | `/tasks` | `201`, созданная задача |
| GET | `/tasks?limit=20&offset=0` | `200`, список задач |
| GET | `/tasks/{task_id}` | `200`, задача |
| PUT | `/tasks/{task_id}` | `200`, полностью заменённая задача |
| DELETE | `/tasks/{task_id}` | `204`, пустое тело |

У задачи четыре поля: положительный `id`, `title` длиной 1–100 символов хотя бы
с одним непробельным символом, целый `priority` от 1 до 5 и булевый `completed`.
Строки вместо чисел и булевых значений не принимаются. PUT полностью заменяет
задачу: пропущенные необязательные поля получают значения по умолчанию.

FastAPI генерирует OpenAPI 3.1 из моделей и маршрутов. Сохранил спецификацию
в `openapi.json`; Schemathesis читает именно этот файл и генерирует валидные
и невалидные запросы для всех пяти операций. Проверки генератора не отключал.
Установил до 25 fuzzing-примеров на операцию; примеры и проверки границ могут
добавлять запросы сверх этого числа. В pytest они отображаются как пять тестов.

```bash
python -m scripts.export_openapi          # обновить спецификацию после изменения API
python -m scripts.export_openapi --check  # проверить без перезаписи
```

Отдельный тест сравнивает сохранённый контракт с `/openapi.json` приложения.
Поэтому изменение модели без обновления файла ломает проверку. Это проверка
реализации по OpenAPI; отдельного consumer-driven контракта между сервисами здесь нет.

## CI и ревью

GitHub Actions запускает линтер, проверку форматирования, сверку OpenAPI
и тесты с покрытием на Python 3.12 и 3.14 при push и в pull request.
Порог покрытия — 95%. JUnit XML и отчёт покрытия сохраняются как артефакты CI.

Изменения подготовил в `lab2`, базовая ветка — `main`. В PR фиксирую результаты
самопроверки и исправления отдельными коммитами. Одобрение другого разработчика
должен поставить внешний ревьюер.

## Ограничения

Данные хранятся в памяти одного процесса и пропадают после перезапуска.
Это учебный стенд без авторизации, БД и проверок нагрузки. Генерация по схеме
не заменяет сценарии с проверкой состояния, поэтому оставил оба вида тестов.
